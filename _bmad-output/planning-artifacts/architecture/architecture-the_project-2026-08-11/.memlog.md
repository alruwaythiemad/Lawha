- (decision) RECOVERY LADDER (FR-6): recovery escalates and remembers. L1 skip failing item -> L2 re-init playback surface without page load -> L3 full page reload (cache NEVER cleared) -> L4 stop responding and let the certified launcher restart the process. - (decision) TIME TRUST (user chose the mechanism): the player takes a server timestamp from every heartbeat response and keeps the offset against a monotonic clock. PREVENTS: Pi and cheap sticks have no RTC, so after a power cut restored at 3am with Wi-Fi still down the player would confidently serve the lunch menu — the wall wrong for hours while the dashboard looks healthy the moment the network returns.

- (decision) TRANSPORT: HTTP heartbeat only for v1. NO websockets, no Supabase Realtime for player sync. Cost of polling: ~43,200 beats/screen/month at ~2KB round trip = ~86MB, about 4 percent of NFR-12's 2GB budget.

- (event) RESEARCH (user asked how the category actually handles media URLs, rather than reasoning from first principles). Xibo (open source, documented player protocol) issues SIGNED HTTP URLs in its RequiredFiles response, re-issued on CONTENT CHANGE not on a timer. Yodeck: S3 encrypted at rest, players cache up to 30 days, two whitelisted IPs. OptiSigns: *.optisigns.com. No vendor found serving media from open public buckets.
- (decision) MEDIA URL MODEL — SUPERSEDES the earlier public-immutable-URL proposal. The real distinction is TIME-scoped signing (breaks offline caching) vs CHANGE-scoped signing (does not). Adopted, matching Xibo: signed GET URLs (R2 is S3-compatible, presigned URLs native) with a generous 7-day TTL, re-issued fresh in every manifest revision. ENABLING INVARIANT: the player's cache is keyed by CONTENT HASH, never by URL — the manifest carries {hash, url} per asset and the player fetches only when the hash is absent from cache, so re-signing costs zero bandwidth. On a 403 the player re-fetches the manifest rather than giving up (covers: pulled a manifest, went dark past the TTL, returned needing an asset never downloaded). PREVENTS: expiring URLs causing a re-download of every asset on every rotation, which would consume NFR-12's entire 2GB budget and surface as an invoice rather than a bug. GAINS over capability URLs: removing a screen or terminating a subscription actually cuts off asset access.
- (decision) NO MEDIA PIPELINE IN V1. Thumbnails (FR-27) generated CLIENT-SIDE at upload — canvas for images, first-frame capture for video — and uploaded alongside; no queue, no server-side compute. No transcoding: FR-26 already guarantees only MP4/H.264, so validation is container and MIME checks on both client and server, and anything that slips through and fails to decode is caught by the player's quarantine ladder and surfaced in the dashboard. Uploads are server-mediated per the fork-2 rule: browser requests a presigned PUT from the API, uploads directly to R2, server then records the media row with hash and size — bytes never pass through the functions.
- (decision) SCHEDULE RESOLUTION: the SERVER resolves precedence once into a WEEKLY RESOLVED TIMETABLE carried in the manifest; the player does no precedence reasoning at all. Rests on a property the PRD does not call out — FR-38 schedules are day-of-week + time-of-day, therefore PERIODIC, so a fully resolved schedule is a 168-hour week that repeats forever rather than an unbounded future timeline. All four precedence rules (screen beats branch, narrower beats wider, later beats earlier, fallback last) collapse into flat segments. PREVENTS the player and dashboard disagreeing about what is playing: the player has no opinion to disagree with, which is stronger than a shared rules package that merely makes two implementations LIKELY to agree. FR-39 becomes free — the dashboard renders the same resolved artifact the player received, not a re-derivation of it.
