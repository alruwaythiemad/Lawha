# Spine Pair Review — the_project (Lawha)

## Overall verdict

This is a high-quality, opinionated spine pair: the direction is genuinely committed, every `{path.to.token}` reference in both files resolves, every numeric contrast claim in DESIGN.md is arithmetically correct, and all three of the load-bearing Chromium 76 capability claims check out. The editorial register is right — DESIGN.md carries voice, most decisions carry their reason, and two invented sections (*The Truth Contract*, *Bilingual Behaviour*) earn their place.

It is not yet safe as a contract. Three holes would each produce wrong code from a competent downstream consumer: the Arabic type ramp is incomplete (`heading-ar` and `body-sm-ar` do not exist, so Arabic headings resolve to a Latin family and fail the Arabic test), the player has no type scale at all while EXPERIENCE.md mandates `vmin` sizing that no token expresses, and the architecture spine's `Provisioning` player state — what the wall shows between "paired" and "playing", i.e. the climax window of the only validated journey — is absent from EXPERIENCE.md's state table.

Secondary but systemic: state coverage is written as global defaults rather than a per-surface matrix, so only one surface's empty state is actually extractable; component coverage is missing one or both halves for seven components that both spines depend on; `mockups/` is linked three times and does not exist; and a triggered *Inspiration & Anti-patterns* section is absent, which is why four of five `.working/` artifacts are orphans.

## 1. Flow coverage — thin

Extracted the requirement groups named in the sources (PRD §6: A Player, B Pairing/screens, C Media, D Playlists, E Scheduling, F Bilingual, G Account/billing, H Website/docs, I Branches) plus the single PRD journey (§3.1, Yusuf). Checked each for a Key Flow with named protagonist, numbered steps, a climax beat, and a failure path. Three flows exist: Flow 1 (Yusuf), Flow 2 (screen goes dark), Flow 3 (branch push).

### Findings

- **high** Group E (Scheduling, FR-38–FR-42/FR-44 plus the four precedence rules) has no Key Flow. It is the group with the sharpest stated UX problem in the sources — "the dashboard surfaces the resolved outcome, not the rule" (PRD Group E) — and the spine's answer is a single Component Patterns paragraph (EXPERIENCE.md:111). No flow walks an owner creating a window that collides with an existing one, so the one sentence that must be generated at the moment of editing ("which window wins and why") has no worked example, no protagonist, and no failure path. A story-dev consumer building the schedule editor has a rule and no scene. *Fix:* add a derived `[ASSUMPTION]` flow for scheduling a lunch window over an all-day window, ending on the resolved-outcome readout, with the collision message as the climax.
- **high** Group G (billing lifecycle: FR-63, FR-63a, FR-63b, FR-63c, FR-79–FR-82) has no Key Flow, despite spanning two surfaces and two registers and ending in content disappearing from a public wall. The behaviour is scattered across State Patterns (EXPERIENCE.md:133–135) and DESIGN.md's holding cards (DESIGN.md:336–341). The trial→warning→stop→restore arc is the second-highest-consequence sequence in the product after a screen going dark. *Fix:* one flow, five steps, climax at the customer-register card appearing on the wall, failure path at payment restored.
- **medium** Flow 1 has no failure path, though its failure modes are enumerated elsewhere (wrong code / expired code / entitlement ceiling, EXPERIENCE.md:105; upload rejection, EXPERIENCE.md:107). Both reference examples close every flow with an explicit `Failure:` line. Flow 1 is the flow that gates success criterion 2 and it is the one with the most enumerated failure modes. *Fix:* add `Failure:` lines to steps 4 and 5 pointing at the existing component rules.
- **medium** Flow 3 has no failure path either — no upload rejection, and nothing for a bulk assignment that partly fails or is undone (the flow claims undoability at EXPERIENCE.md:113 but never exercises it). *Fix:* one failure line covering the undo.
- **medium** FR-11 is cited nowhere in either spine. It is a user-visible propagation rule: "the item currently on screen plays to the end of its duration before the change takes effect, unless that item was itself removed." Flow 3 step 5 (EXPERIENCE.md:251) describes propagation as immediate-then-heartbeat-confirmed and omits the item-completion delay entirely, so an owner watching a wall after a bulk push sees a lag the spine does not predict and the console does not explain. The memlog shows FR-11 was read during discovery (`.memlog.md:33`) and then dropped. *Fix:* state FR-11's delay in Flow 3 step 5 and in the Playlist editor pattern.
- **low** Flows 2 and 3 have no named protagonist ("the owner", "Owner"). This is disclosed and defended in both headers, and the memlog decision (`.memlog.md:37`) explicitly forbids inventing one. Recorded as a known deviation from the reference shape rather than a defect.
- **low** No flow covers re-pairing (FR-23) or removing a screen (FR-22), both of which have destructive-confirmation rules in Interaction Primitives (EXPERIENCE.md:145) that are never exercised.

## 2. Token completeness — thin

Extracted all frontmatter tokens (20 colors, 10 typography, 6 rounded, 7 spacing, 17 components) and every `{path.to.token}` reference in the prose of both files. **All references resolve; nothing is dangling in either direction.** Recomputed every stated contrast ratio from sRGB relative luminance: `21:1`, `5.74:1`, `7.47:1`, `3.73:1`, `5.63:1`, `12.1:1` and the amber-fails-as-text claim are all **correct**. Fourteen orphan tokens (defined, never referenced) were also checked; most are deliberate (`rounded.sm/md/lg/xl` are all 0 by design).

### Findings

- **critical** The Arabic type ramp is incomplete. `typography` defines `display-ar`, `body-ar`, `label-ar` — but no `heading-ar` and no `body-sm-ar`, while `heading` (18px) and `body-sm` (13px) both hardcode `fontFamily: Inter` (DESIGN.md:45–62). `{components.nav-item}` and `{components.holding-card-*}` typography resolve through `body-sm`. Inter has no Arabic coverage, so an Arabic heading or nav label rendered from these tokens falls back to a host font — the exact failure FR-51/FR-52 and AD-23 exist to prevent, and the exact thing success criterion 3 is judged on ("no fallback font"). DESIGN.md:278 asserts "Arabic line-heights run higher **across the ramp**", which is only true for the three tiers that exist. *Fix:* add `heading-ar` and `body-sm-ar` (Cairo, `letterSpacing: 0`, raised line-height), or state a single resolution rule — "every `X` token has an `X-ar` counterpart; Latin families never render Arabic" — and enumerate the pairs.
- **critical** There is no player type scale, and the two spines contradict each other on how player type is sized. EXPERIENCE.md:187 commits: "on-screen type is sized in `vmin` units rather than pixels — `clamp()` does not exist at the Chromium 76 floor, and `vmin` scales correctly on 720p and 4K panels alike." DESIGN.md contains **zero `vmin` values**; every typography token is in `px`, and the largest is `{typography.code}` at 56px — which is specifically the pairing code, a player string that must be legible at 2–4 metres (DESIGN.md:271, EXPERIENCE.md:187). At 56px on a 1080p panel that is 5.2% of viewport height; at 4K it is 2.6% and unreadable across a café. The player's holding cards, pairing instructions, and trial badge therefore have no size tokens at all. *Fix:* add a player tier (`player-code`, `player-headline`, `player-body`) in `vmin`, or make `{typography.code}` `vmin`-valued and state the px/vmin boundary explicitly (console = px, player = vmin).
- **high** The `-dark` suffix carries two incompatible meanings, and a naive resolver inverts a load-bearing decision. In `colors`, `-dark` means "the dark-theme value of this token." In `{components.holding-card-customer}` (DESIGN.md:213–216) `background-dark` and `muted-foreground-dark` are used as literal near-black values on a player that has no theme — the whole point of the customer register being that it is dark, unbranded, and non-embarrassing on a public wall (FR-63b). Any consumer applying the obvious rule (in dark mode, swap `X` → `X-dark`) either leaves this card unchanged by accident or, reading it as already-dark, flips it to white. *Fix:* give the player card its own non-theme tokens (`player-neutral-ground`, `player-neutral-ink`) and reserve the `-dark` suffix strictly for theme pairs.
- **high** No component token declares its dark-mode resolution. Every one of the 17 `components` objects references only light tokens — `{components.nav-item-active}` is `background: {colors.foreground}` / `foreground: {colors.background}` (DESIGN.md:200–203), which in dark mode must become `{colors.foreground-dark}` / `{colors.background-dark}` and nowhere says so. DESIGN.md:261 states the principle ("Dark mode is inversion, not a re-tune") but the components layer, which is the machine-readable half a code generator consumes, has no rule. Four dark tokens (`foreground-dark`, `divider-dark`, `input-dark`, `electric-foreground-dark`) are consequently referenced by nothing at all. *Fix:* one sentence in *Colors* — "component tokens name light-mode values; the dark surface substitutes the `-dark` counterpart of every color token except `alarm`, `alarm-foreground`, `amber`, `amber-foreground`" — which also fixes the finding above.
- **high** The focus ring is unusable on the product's loudest component. `{components.focus-ring}` is `2px solid {colors.electric}` with no signal-surface variant, and EXPERIENCE.md:103 puts a link inside the alarm banner ("links to the disclosure"). Computed: `{colors.electric}` `#0F2BFF` against `{colors.alarm}` `#FF2D00` is **2.00:1**; in dark mode `{colors.electric-dark}` `#5C7CFF` against the same red is **1.03:1** — effectively invisible. Both fail WCAG 2.2 SC 1.4.11 / 2.4.13, on the one control in the product that an owner must reach in a hurry. The spine forbids the two obvious escapes ("never suppressed, never replaced by a background change", DESIGN.md:332). The banner's link colour is also unspecified: electric text on the red fill is 2.00:1. *Fix:* define a focus ring variant on signal fills (black or white ring), and state the alarm banner's link treatment (black text, underlined, black ring).
- **medium** `{colors.divider}` `#DADADA` is **1.40:1** on white (`divider-dark` is **1.38:1** on `background-dark`). DESIGN.md:253 sets the rule "never the only thing distinguishing two interactive targets" — and then the system's primary unit violates it: `{components.table-row}` is separated only by `divider` (DESIGN.md:151–155) while EXPERIENCE.md:99 makes "the whole row is one link". Adjacent link targets separated at 1.40:1. *Fix:* either raise `divider` to ≥3:1 against ground, or state that row separation is non-normative and the row's accessible name is the sole boundary (and drop the rule it contradicts).
- **medium** `{typography.code}` (56px, tracking 0.1em) is Latin-only and DESIGN.md:271 justifies it as the pairing code read across a café. FR-15 requires the code screen to render "instructions in the configured language" — so the pairing card carries Arabic instructional text beside a Latin code, and no token pairs the two. Related to the missing player tier above. *Fix:* specify the pairing card's Arabic instruction tier explicitly.
- **medium** `{components.trial-badge}` has no colour. It defines `opacity: 0.3`, `maxAreaRatio`, `marginZone`, `motion`, `mirrors` — but no `foreground`, and it composites over arbitrary customer content (FR-79–FR-82). 0.3 opacity of what, against a photo of a menu? *Fix:* name the mark's colour and whether it inverts, or state a fixed treatment (white mark, 0.3, no outline).
- **low** DESIGN.md:261 claims `#0F2BFF` on near-black is "2.5:1". Computed: **2.65:1**. The conclusion (unreadable, hence `electric-dark`) is right; the number is wrong and this file's other numbers are exact.
- **low** EXPERIENCE.md:193 claims contrast is "largely settled by the palette — 21:1 ink on ground". True in light mode; dark mode is **19.80:1** (`#FFFFFF` on `#0A0A0A`), because `background-dark` is deliberately not `#000000`. *Fix:* "21:1 light, 19.8:1 dark."
- **low** `{spacing.rule}` (1px) is defined and referenced by nothing — all eight component borders hardcode `'1px solid …'`. A consumer changing the token changes nothing. *Fix:* reference it, or drop it.
- **low** DESIGN.md:273 states the label tier is "defined by weight 800 at 10–11px in `{colors.muted-foreground}`, **and by nothing else**", but five components apply `{typography.label}` at full-strength foreground or on a signal fill (`group-header`, `nav-item-active`, and all three status tags). The absolute reads as normative and is contradicted by the frontmatter directly above it. *Fix:* "in `{colors.muted-foreground}` unless the component names its own foreground."
- **low** `{colors.amber}` fill is **1.73:1** against white — the lowest-contrast surface in the palette, on a component whose stated job is to be impossible to overlook (DESIGN.md:326). Its black label carries the meaning at 12.11:1 so this is not a failure, but the "solid block" escalation logic is weakest exactly where the spine assumes it is strong. Worth a sentence acknowledging the caveat tag reads quieter than the alarm tag by design.

DESIGN.md `{components.table-row}` / "**Table row** — the console's primary unit" (DESIGN.md:322) vs EXPERIENCE.md "**Screen row**" (EXPERIENCE.md:99). `{components.meter}` vs "**Storage meter**". `{components.nav-item}` vs "**Navigation**". ## 4. State coverage — adequate

Walked all eleven console surfaces in the IA table and all six player states. EXPERIENCE.md declares the right rule — "Every surface specifies all of: empty, loading, partial, error, and where applicable stale, at-limit, and stopped" (EXPERIENCE.md:121) — and the individual state *patterns* are strong, several of them better than the reference examples (partial-load honesty, at-limit shape, stale-is-not-an-error). Permission-denied is correctly N/A and correctly justified (one actor, EXPERIENCE.md:26). The gap is per-surface resolution: the section states defaults and one concrete instance.

### Findings

- **high** The architecture spine's `Provisioning` player state is missing from EXPERIENCE.md's state table (EXPERIENCE.md:48–56). ARCHITECTURE-SPINE.md:319 has `Provisioning --> Playing: revision fully cached`, and AD-5 guarantees a revision activates *only* when fully cached — so there is a real, sometimes minutes-long window where the screen is paired, has a manifest, and cannot play yet. That window is Flow 1 between step 6 and step 7: the climax of the only validated journey, the fifteen-minute test, with Yusuf standing in front of the TV. Nothing says what is on the wall, in which register, or whether it shows progress. `Nothing to play` is triggered by "no playlist assigned" and does not cover it; `Playing` requires a cached revision. FR-14 (recover from partial cache by re-fetching) lands here too and is cited nowhere. *Fix:* add a `Provisioning` row, owner register, with what it says while first-caching and what it says on re-cache mid-life (when a venue's customers are watching, so the register may need to switch).
- **high** No surface specifies offline or connection-loss behaviour for the **console**. The player's offline story is excellent and correct ("offline is the normal operating case", matching ARCHITECTURE-SPINE.md:332). But when the owner's own browser loses connectivity, the dashboard is showing derived statuses computed from a `last_seen` it can no longer refresh (AD-12 makes status a read-time function) — a dashboard that keeps displaying "Live" while unable to reach the server is precisely the class of claim *The Truth Contract* exists to forbid. Both reference examples specify a global offline state. *Fix:* one row — console offline shows a persistent notice and marks every status as of the last successful fetch time.
- **medium** Per-surface empty states are missing for nine of eleven surfaces. Only Screens is specified (EXPERIENCE.md:123, and it is well done). Media, Playlists, Playlist editor, Schedules, Branches, Billing, Settings, Screen detail have no empty, no error, and no at-limit copy of their own; a consumer has a principle ("empty is instructional, never decorative") and no strings. Note the interaction: Playlists-empty and Media-empty are both reachable inside Flow 1, since the entry point to a playlist is Media. *Fix:* keep the defaults section and add the `State | Surface | Treatment` table both examples use, with one row per surface that overrides or instantiates a default.
- **medium** EXPERIENCE.md:137 claims "Player states never fail visibly. No browser error page, no blank screen, no stack trace, **in any circumstance** (FR-12)." That absolute is false for the best-effort tier and the sources say so twice: PRD §4.3 ("a crash or a power cut leaves the screen dark until someone intervenes") and ARCHITECTURE-SPINE.md:326 (`Recovering --> Halted: L4 hand to launcher`, unrecoverable where there is no launcher). A dark screen is a blank screen. The spine's own FR-6a caveat tag exists precisely because of this. Stating an unachievable absolute is worse than stating the boundary. *Fix:* "…in any circumstance the player is still running. On best-effort devices process death is unrecoverable and the wall goes dark — this is what `{components.status-tag-caveat}` discloses."
- **medium** The `Recovering` state is marked register "Invisible" (EXPERIENCE.md:55), but ARCHITECTURE-SPINE.md:324 escalates through `Reloading` — an L3 full page reload. A page reload on a 1920×1080 wall is a visible flash and a return through `Provisioning`, which is also unspecified. *Fix:* state what a reload looks like on the wall (hard cut from and to what), or specify that the last frame is held.
- **low** Player `Between windows` is customer-register with no text (correct per FR-63b's spirit), but the state is entered by a schedule gap with no fallback (FR-40) — an owner-caused misconfiguration that the console should surface. Nothing in the console's state patterns flags "this screen has a gap with no fallback". *Fix:* one line in the Schedules surface states.

## 6. Bloat & overspecification — adequate

### Findings

A consumer extracting rules must read an unheaded block. *Fix:* keep the two-consumer framing, move the ban list to the single place it is enforced.
- **low** *The Truth Contract*'s four rules restate FR-18, FR-19, FR-20 and FR-6a close to verbatim. Defensible — it is the section that governs the rest and is cross-referenced from three places — but it is source restatement and could carry the FR pointer plus the UX consequence rather than the requirement text.
